# Agent Note: 在下一次提供方请求前终止失控轮次

Status: implemented

[English](2026-08-19-runaway-turn-circuit-breaker.md) | 中文

## 问题

模型可能持续生成形式正确的工具调用，恢复监听器也可能不断重试失败请求。这两条路径在状态机看来都在正常推进，因此此前的循环没有终止条件。一个很小的用户请求可能持续消耗提供方额度，直到外部余额或进程限制将其停止。仅限制并行工具调用没有作用，因为这些请求仍然是串行且逐次有效的。

## 决策

`AgentLoop` 拥有三个正数部署上限：单轮步骤数、单步骤提供方尝试次数、单轮累计上报 Token。driver 在准备下一个模型步骤前检查步骤与 Token 上限；同一步重试达到尝试次数后会被拒绝。三条路径都以 `AGENT_LOOP_CIRCUIT_OPEN` 结束持久轮次；该失败在 `agent/request-error` 之外抛出，因此请求恢复逻辑不能继续重试熔断器本身。

Token 计数器累加每次提供方尝试上报的互斥输入、输出、缓存读取和缓存写入字段。推理 Token 不重复累加，因为它已包含在输出 Token 内。某次工具调用跨过 Token 上限时，会先完成并持久化工具结果，再阻止下一个模型请求。最终响应跨过上限时仍按成功处理，因为它不会产生后续消耗。新的用户轮次重新计数。

包默认值为复杂自动化保留足够空间：64 个步骤、每步 8 次尝试、2,000,000 个上报 Token。企业桌面覆盖层使用 24 个步骤、4 次尝试和 500,000 个上报 Token。这些字段不进入用户 Settings，因此受管客户端无法关闭该安全策略。

## 备选方案

**检测完全相同的工具名和参数。** 不作为主要熔断手段：轮询、分页读取、终端写入和状态检查都可能合理地重复同一签名。确定性的资源上限更容易审计，也不会被轻微修改参数绕过。

**只依赖提供方配额或 LiteLLM 余额。** 不予采用：它会在已经产生不必要消耗后才终止事故，客户端也得不到精确、持久的失败原因。网关配额保留为第二层保护，而不是第一层熔断。

**把上限开放为用户设置。** 不予采用：在受管部署中，本地用户可能放宽企业保护。受信部署仍可通过组合配置调整。

**在客户端增加金额上限。** 暂缓：模型价格与租户策略属于 LiteLLM／AI Hub；客户端没有可信的价格表。

## 影响

合理任务达到上限时会明确结束，而不是无限继续。对话记录保留已经完成的消息和工具结果，UI 会用本地化安全提示替代内部英文诊断。不上报用量的提供方无法使用 Token 上限，但独立的步骤和尝试次数上限仍会终止其循环。运维人员可以通过稳定错误码在会话审计中识别每次熔断。
