# Agent Note：Harness 与受管能力的统一升级时机

状态：已实现

[English](2026-08-18-managed-client-plugin-upgrades.md) | 中文

## 问题

Harness 新版本、AI Hub 中已授权能力的版本替换，以及新授权或撤销代表不同的用户意图。版本升级不应分别弹窗或强制打断当前工作；新授权和撤销则会改变可用拓扑。桌面生产环境仍禁用 HMR，因此需要重启的制品只能在进程边界激活。

## 决策

Electron 将 Harness 客户端版本与 MCP、Tool、Skill、Bundle、客户端插件的原位版本替换收敛到同一个受管升级队列。AI Hub 目录按类型、稳定 `externalRef` 及 MCP 内 Tool 的父级路径比较；只有引用集合不变且 `releaseVersion` 变化时才认定为升级。新授权、撤销和混合拓扑变化继续走普通对账路径；企业指令仍是下一次模型请求生效的独立热加载通道。

统一升级状态通过 context-isolated preload 窄桥发布。即使没有 `PLUGIN_MARKET` 菜单权限，侧边栏仍显示小型下载图标。点击后一次展示全部待升级项，并提供两种时机：

- **下次启动时静默升级**：当前进程不变。能力制品由下次启动期对账在后端启动前安装；Harness 目标平台与版本会持久化，下次身份验证后自动下载并安装，不再弹出 Harness 确认。
- **立即下载并重启**：统一下载、校验并原子替换全部待升级能力，再执行客户端安装或 Harness 重启。Windows 使用 `electron-updater` 的 SHA-512 校验与 `quitAndInstall`；macOS 将经 SHA-256 校验的 DMG/PKG 交给操作系统安装程序。

## 替代方案

- **每种升级维护独立弹窗**：会在 Harness、插件和能力同时有新版本时连续打断用户，且无法统一安排下次启动。
- **检测后立即自动下载**：会在未经用户选择时消耗带宽并改变磁盘制品，不符合可选升级边界。
- **把新授权也当作可延后升级**：会混淆管理员主动下发与用户版本选择，并使撤销后的旧能力停留更久。

## 后果

所有需要重启的升级使用同一个可发现入口，不会在后台检测时弹出模态框。已安排、正在下载和失败状态都通过同一图标可见；失败不破坏当前版本，并保留重试入口。客户端延后计划需要一份非敏感的本地版本指针；能力延后计划无需另存日志，因为启动期授权目录对账本身就是权威状态。

## 验证

桌面客户端测试覆盖 MCP、Tool、Skill 和插件的稳定引用版本替换，并与新授权拓扑变化区分。侧边栏组件测试覆盖无市场菜单权限时的统一升级图标；静态桌面契约测试固定统一 IPC 通道、延后计划和 `electron-updater` 边界。
